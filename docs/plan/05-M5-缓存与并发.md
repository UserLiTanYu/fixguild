# M5：缓存与并发

> 里程碑：M5（第一部分）· 状态：未开始 · 预计 0.5–1 周  
> 关联设计：[11-缓存设计](../design/11-缓存设计.md) · [10-并发幂等与事务](../design/10-并发幂等与事务.md) · [08-多租户与权限](../design/08-多租户与权限.md)

---

## 1. 目标

在不破坏正确性的前提下，为读多写少的数据加缓存，为工单关键命令加分布式锁：

- 权限、字典、租户信息命中缓存；
- 权限变更通过版本号即时生效，不 `SCAN` 删除；
- 工单号生成并发不重复；
- 派单/接单/完工等命令有声明式分布式锁；
- 锁与事务边界正确。

---

- M2 权限模型完成；
- M3 工单命令接口完成；
- M4 消息链路稳定；

- 跨机房缓存同步。

## 4. 任务清单

### 4.1 Redis 接入

- [ ] `common/pom.xml` 增加 `spring-boot-starter-data-redis`、`redisson-spring-boot-starter`
- [ ] 配置 `spring.data.redis.*`，local/dev/prod 分别配置
- [ ] local 测试策略：
  - 优先用 Docker Redis；
  - 若本机没有 Redis，提供 `@ConditionalOnProperty` 的本地缓存实现或测试 Mock，保证 `mvn test` 不强依赖 Redis
- [ ] 统一序列化：String key + JSON value，禁止 JDK 序列化
- [ ] 缓存 Key 统一带租户，避免串租户

### 4.2 权限缓存

- [ ] Key 规范：
  - `auth:version:{clientCode}:{tenantId}`：整数版本号
  - `auth:info:{clientCode}:{tenantId}:{userCode}:{version}`：权限/角色/菜单
- [ ] 登录/鉴权：
  - 先读版本号
  - 版本号不存在时初始化为 1
  - 拼 key 读缓存，未命中查库并回填
  - TTL 30 分钟
- [ ] 变更失效：
  - 用户角色变更、角色菜单变更、角色停用、菜单权限变更时 `INCR auth:version:*`
  - 旧版本 key 自然过期，不 `SCAN`
- [ ] `StpInterfaceImpl` 改为从 `AuthService` 读取缓存
- [ ] 测试：角色变更后旧权限立即失效

### 4.3 业务缓存

- [ ] 字典缓存
  - Key：`dict:{dictType}`
  - TTL：1 小时
  - 字典变更时删除
- [ ] 租户信息缓存
  - Key：`tenant:info:{tenantId}`
  - TTL：10 分钟
  - 租户变更/启停时删除
- [ ] Caffeine 本地缓存只放字典、租户这类极热数据，TTL 短于 Redis
- [ ] 工单列表不缓存，靠索引

### 4.4 工单号序列

- [ ] 实现 `WorkOrderNoGenerator`
  - Key：`seq:workorder:{tenant}:{yyyyMMdd}`
  - `INCR` 后补 6 位
  - TTL 2 天
  - 格式：`WO + yyyyMMdd + 000001`
- [ ] M3 如果用了数据库临时方案，本阶段迁移到 Redis
- [ ] 并发测试：100 个线程同时创建，工单号不重复

### 4.5 登录失败记录

- [ ] 将 `LoginAttemptGuard` 从 `ConcurrentHashMap` 迁移到 Redis
- [ ] Key：`login:fail:{client}:{tenant}:{username}`
- [ ] TTL 15 分钟
- [ ] 登录成功删除
- [ ] 多实例部署时锁定状态一致
- [ ] 保留本地内存实现作为 local 降级方案（可选）

### 4.6 分布式锁

- [ ] `@DistributedLock` 注解：
  - `key` 支持 SpEL
  - `waitTime`
  - `leaseTime`
  - `errorMsg`
- [ ] AOP 实现：
  - 解析 SpEL
  - 加锁失败抛业务异常
  - `finally` 解锁，只解自己的锁
- [ ] 锁的粒度：
  - `lock:workorder:assign:{tenant}:{orderUid}`
  - `lock:workorder:accept:{tenant}:{orderUid}`
  - `lock:workorder:complete:{tenant}:{orderUid}`
  - `lock:seq:workorder:{tenant}:{date}`
- [ ] 锁与事务：
  - 锁包住事务
  - 释放锁在事务提交之后
  - 推荐“门面服务加锁 + 事务服务执行”两层结构
  - 租约时间大于事务耗时，或使用看门狗
- [ ] M3 的命令服务接入锁，保留乐观锁作为第二道防线

### 4.7 测试

- [ ] 权限缓存命中、过期、版本号失效
- [ ] 字典/租户缓存变更后删除
- [ ] 工单号 100 并发不重复
- [ ] 登录失败锁定多实例一致
- [ ] 分布式锁：并发派单只有一个成功
- [ ] 锁异常释放：业务抛异常后锁可再次获取
- [ ] 缓存与数据库一致性：先更新 DB 再删缓存

## 6. 风险与注意事项

- 不要在 `TenantFactory` 或业务代码里硬编码租户。
- 所有缓存 Key 必须带租户；平台全局数据用 `0`。
- 缓存更新顺序：先更新 DB，再删缓存；不要先删缓存再更新 DB。
- 权限缓存用版本号，禁止 `SCAN` 删除旧 key。
- 分布式锁不能替代乐观锁；两者同时保留。
- 锁的 key 必须包含租户和业务 uid，避免跨租户互斥。
- 看门狗模式要确认 Redisson 配置，避免租约过期业务未完成。
- local 测试不要强制启动 Redis，否则 CI 和新人环境成本过高。
