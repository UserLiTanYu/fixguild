# M3：工单核心

> 里程碑：M3 · 状态：未开始 · 预计 1 周  
> 关联设计：[03-领域模型](../design/03-领域模型.md) · [04-工单状态机](../design/04-工单状态机.md) · [05-数据库设计](../design/05-数据库设计.md) · [10-并发幂等与事务](../design/10-并发幂等与事务.md)

---

## 1. 目标

完成工单核心闭环：

```text
创建 → 派单 → 接单 → 开始 → 完工 → 确认
          ↘ 拒单 → 待派单
          ↘ 取消
```

同时落地技师、客户、设备三个基础档案，保证状态流转正确、并发安全、请求幂等、租户隔离。

---

## 2. 前置条件

- M2 完成：三端登录、RBAC、权限注解、数据范围。
- `sys_user` 中存在技师端账号，并且可以关联 `technician.user_id`。
- `docs/sql/schema.sql` 中工单相关表已存在；本阶段重点是补齐 H2 表与 Java 实现。

---

## 3. 范围

### 做

- 技师、客户、设备基础档案 CRUD；
- 工单、工单日志、附件元数据、派工记录、请求幂等；
- 工单状态机与全部命令接口；
- 乐观锁、请求幂等；
- 技师“只看自己的工单”；
- 平台端全局工单查询；
- 状态机单元测试、并发测试、隔离测试。

### 不做

- MQ 通知（M4）；
- 真实的文件上传/下载（M5，本阶段只存附件元数据）；
- Redisson 分布式锁（M5，本阶段先用乐观锁保证正确性）；
- 自动派单算法（M7）；
- 客户 H5 报修（M7）。

## 4. 任务清单

### 4.1 基础档案

- [ ] H2 表：`technician`、`customer`、`equipment`，字段与 `docs/sql/schema.sql` 对齐
- [ ] 实体：
  - `TechnicianEntity extends TenantEntity`
  - `CustomerEntity extends TenantEntity`
  - `EquipmentEntity extends TenantEntity`
- [ ] Mapper、Param、VO、Service、Controller
- [ ] 技师接口
  - `POST /tenant/api/technician/page`
  - `POST /tenant/api/technician/create`
  - `POST /tenant/api/technician/update`
  - `POST /tenant/api/technician/status`
  - `POST /tenant/api/technician/workload`
- [ ] 客户接口
  - `POST /tenant/api/customer/page`
  - `POST /tenant/api/customer/create`
  - `POST /tenant/api/customer/update`
  - `POST /tenant/api/customer/detail`
- [ ] 设备接口
  - `POST /tenant/api/equipment/page`
  - `POST /tenant/api/equipment/create`
  - `POST /tenant/api/equipment/update`
  - `POST /tenant/api/equipment/detail`
- [ ] 技师账号绑定：`technician.user_id` 关联 `sys_user.id`，技师登录后能定位自己的档案
- [ ] 手机号、身份证字段先保留密文/哈希列；明文录入与展示在 M5 加密能力完成后开放
- [ ] 基础档案种子数据：至少 2 个租户、每租户 2 名技师、2 个客户、3 台设备

### 4.2 工单数据模型

- [ ] H2 表：
  - `work_order`
  - `work_order_log`
  - `work_order_attachment`
  - `work_order_dispatch`
  - `work_order_command`
- [ ] 实体：
  - `WorkOrderEntity extends TenantEntity`（表字段齐全）
  - `WorkOrderDispatchEntity extends TenantEntity`（表字段齐全）
  - `WorkOrderLogEntity`：没有 `update_by/update_time/is_delete`，用轻量实体，只映射现有列
  - `WorkOrderAttachmentEntity`：没有 `create_by/update_by/update_time/remark`；轻量实体，`is_delete` 加 `@Column(isLogicDelete = true)`
  - `WorkOrderCommandEntity`：没有 `create_by/update_by/remark/is_delete`，用轻量实体
  - 轻量实体的 `tenant_id` 字段必须加 `@Column(tenantId = true)`，否则租户插件不生效
- [ ] Mapper、Param、VO
- [ ] 工单号生成器
  - 格式：`WO + yyyyMMdd + 6 位序号`
  - 建议使用 Redis `INCR seq:workorder:{tenant}:{date}`，设置 2 天过期
  - 如果本阶段不想引入 Redis，可先用数据库唯一索引 + 重试，M5 迁移到 Redis
  - 必须保证同一租户同一天并发创建不重复
- [ ] 工单列表冗余字段：`customer_name`、`equipment_name`、`technician_name`

### 4.3 工单查询与创建

- [ ] 工单分页 `POST /tenant/api/work-order/page`
  - 筛选：状态、优先级、技师、关键字、创建时间范围
  - 默认排序：`create_time DESC, id DESC`
  - 技师端强制追加 `technician_id = 当前技师`
- [ ] 工单详情 `POST /tenant/api/work-order/detail`
  - 返回工单、客户、设备、技师、日志时间线、附件元数据
- [ ] 工单新增 `POST /tenant/api/work-order/create`
  - 校验客户、设备属于当前租户
  - 写工单 + 创建日志 + 幂等记录，同一事务
  - 支持附件元数据列表
- [ ] 工单编辑 `POST /tenant/api/work-order/update`
  - 只允许在 `PENDING`、`ASSIGNED` 状态修改标题、描述、优先级、期望时间
- [ ] 平台端全局工单查询（可选，时间允许再做）
  - `POST /platform/api/work-order/page`
  - `POST /platform/api/work-order/detail`
  - 使用 `@IgnoreTenant` + 平台权限，必须记录跨租户查询日志

### 4.4 状态机与命令接口

- [ ] `WorkOrderStatus` 枚举与合法流转表
  - `PENDING → ASSIGNED / CANCELED`
  - `ASSIGNED → ACCEPTED / PENDING / CANCELED`
  - `ACCEPTED → IN_PROGRESS / CANCELED`
  - `IN_PROGRESS → COMPLETED / CANCELED`
  - `COMPLETED → CONFIRMED / IN_PROGRESS`
  - `CONFIRMED`、`CANCELED` 为终态
- [ ] `WorkOrderAction` 枚举：`CREATE/ASSIGN/ACCEPT/REJECT/START/COMPLETE/CONFIRM/CANCEL/REOPEN`
- [ ] 统一命令方法：
  - 校验租户、权限、当前状态
  - 乐观锁更新：`version + 1`、`status = target`
  - 写 `work_order_log`，记录 `from_status/to_status/operator/trace_id`
  - 派单/拒单写 `work_order_dispatch`
  - 事务提交后发布领域事件（M4 接入 MQ，本阶段可先留接口）
- [ ] 接口：
  - `POST /tenant/api/work-order/assign`
  - `POST /tenant/api/work-order/cancel`
  - `POST /tenant/api/work-order/confirm`
  - `POST /tenant/api/work-order/reopen`
  - `POST /technician/api/work-order/accept`
  - `POST /technician/api/work-order/reject`
  - `POST /technician/api/work-order/start`
  - `POST /technician/api/work-order/complete`
  - `POST /technician/api/work-order/page`
  - `POST /technician/api/work-order/detail`
  - `POST /technician/api/work-order/today`
- [ ] 守卫条件：
  - 派单：技师存在、状态可用
  - 接单/拒单/开始/完工：工单必须属于当前技师
  - 完工：填写完工说明，至少 1 张照片
  - 取消/返工：填写原因
- [ ] 状态变更时间字段：`assign_time/accept_time/start_time/finish_time/confirm_time/cancel_time`

### 4.5 并发与幂等

- [ ] 乐观锁 SQL：`version = #{version}` + `status = #{fromStatus}` + `is_delete = 0`
- [ ] 影响行数为 0 返回 409，提示刷新重试
- [ ] 请求幂等：
  - 写接口必须传 `X-Request-Id`（或请求体 `requestId`）
  - `work_order_command` 唯一键 `(tenant_id, request_id)`
  - `PROCESSING` 重复请求返回 409
  - `SUCCESS` 重复请求返回第一次结果
  - `FAILED` 允许重试
- [ ] 事务边界：工单 + 日志 + 派工 + 幂等记录在同一事务
- [ ] 第三方调用（短信、文件）不得放在事务内

### 4.6 权限与数据范围

- [ ] 租户端工单接口加 `tenant:work-order:*` 权限
- [ ] 技师端工单接口加 `tech:work-order:*` 权限
- [ ] 技师端查询/详情/命令强制校验 `technician_id`
- [ ] 租户调度员可查看本租户全部工单
- [ ] 平台跨租户查询必须 `@IgnoreTenant` + `platform:work-order:*`

### 4.7 测试

- [ ] 状态机单元测试
  - 所有合法流转成功
  - 所有非法流转抛业务异常
  - 终态不可再流转
- [ ] 集成测试
  - 创建 → 派单 → 接单 → 开始 → 完工 → 确认完整链路
  - 拒单回到 `PENDING`
  - 取消、返工
- [ ] 并发测试

  - 100 个线程同时创建，工单号不重复
  - 同一 `requestId` 重复创建 10 次，只产生 1 条工单
- [ ] 租户隔离
  - 租户 B 按 uid 查租户 A 工单返回 404
  - 技师不能接其他技师的工单
- [ ] 基础档案 CRUD 与分页测试

- [ ] 工单完整闭环可走通，状态机覆盖全部合法流转

- [ ] 同一 `requestId` 重复创建只产生 1 条工单

- [ ] 租户隔离测试通过
- [ ] 工单日志包含 `from_status/to_status/operator/trace_id`
- [ ] `mvn test` 通过，Swagger、H2、`api-examples.http` 已同步

---

## 6. 风险与注意事项

- 状态机是核心，先写单元测试再写 Controller。
- 乐观锁必须带 `status` 条件，避免旧状态覆盖新状态。
- 事务内不要发 MQ；事件发布接口先留好，M4 再接。
- 附件只存元数据，不要在 M3 实现文件上传。
- 工单号生成方案一旦确定，并发测试必须覆盖。
- 技师照片校验在 M5 文件上传完成后补真实校验，M3 先校验附件数量。
