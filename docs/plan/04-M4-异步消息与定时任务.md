# M4：异步消息与定时任务

> 里程碑：M4 · 状态：未开始 · 预计 1 周  
> 关联设计：[09-异步消息与定时任务](../design/09-异步消息与定时任务.md) · [07-关键时序](../design/07-关键时序.md) · [10-并发幂等与事务](../design/10-并发幂等与事务.md)

---

## 1. 目标

把工单状态变更的副作用从主链路剥离：

- 核心写操作同步完成，通知/统计等副作用走 MQ；
- 消息可重试、可补偿、消费幂等；
- 超时提醒、自动确认、统计等定时任务可重复执行且结果一致。

---

## 2. 前置条件

- M3 完成：工单状态机、派单/接单/完工链路可运行。
- `work_order`、`work_order_log`、`work_order_dispatch` 已稳定。
- Docker Compose 可启动 MySQL、Redis；本阶段新增 RocketMQ、XXL-Job。

---

## 3. 范围

### 做

- RocketMQ 5.x/4.9.x 接入；
- 事务提交后发送领域事件；
- 泛型消费者基类、消费幂等、失败表；
- 站内信 + Mock 短信通知；
- XXL-Job 超时扫描、自动确认、每日统计、MQ 失败重试；
- 重复消息、消费者宕机、Job 重复执行的测试。

### 不做

- 真实短信供应商；
- 客户 H5 通知；
- 导出恢复任务（依赖 M5 的 `export_task`，在 M5 补）；
- 复杂消息路由和消息轨迹平台。

## 4. 任务清单

### 4.1 基础设施

- [ ] `pom.xml` 增加 RocketMQ、XXL-Job 依赖，版本统一在根 `dependencyManagement`
- [ ] `docker-compose.yml` 增加：
  - `rocketmq-namesrv`
  - `rocketmq-broker`
  - `rocketmq-console`（可选）
  - `xxl-job-admin`
- [ ] `application.yml`、`application-dev.yml`、`application-prod.yml` 增加 NameServer、生产者组、消费者组、XXL-Job 配置
- [ ] 所有地址、密钥走环境变量，不提交真实配置

### 4.2 事件生产

- [ ] 定义事件类型与消息信封：
  - `WORK_ORDER_CREATED`
  - `WORK_ORDER_ASSIGNED`
  - `WORK_ORDER_ACCEPTED`
  - `WORK_ORDER_REJECTED`
  - `WORK_ORDER_STARTED`
  - `WORK_ORDER_COMPLETED`
  - `WORK_ORDER_CONFIRMED`
  - `WORK_ORDER_CANCELED`
  - `WORK_ORDER_TIMEOUT`
- [ ] Topic：`fixguild_topic${mq.env-suffix}`
- [ ] Tag 与事件类型一一对应
- [ ] `EventPublisher`：
  - 有事务时注册 `TransactionSynchronization.afterCommit`
  - 无事务时直接发送
  - 发送失败写 `msg_fail`
  - 消息体带 `eventId/eventType/tenantId/traceId/timestamp/payload`
- [ ] M3 的状态命令改为发布事件，不直接调通知服务

### 4.3 消息消费

- [ ] `AbstractRocketMQConsumer<T>`：
  - 泛型消息解析
  - 最大重试次数 3
  - 抽象 `handleMessage(T)`
  - 抽象 `idempotentKey(T)`
- [ ] 消费幂等 `mq_consume_log`
  - 唯一键 `(topic, consumer_group, msg_id)`
  - 首次插入 `PROCESSING`
  - 成功更新 `SUCCESS`
  - 失败更新 `FAILED` 并抛异常触发重试
  - 重复消息 `SUCCESS` 直接 ACK
- [ ] 失败表 `msg_fail`
  - 超过重试次数写 `DEAD`
  - 保留 `topic/tag/msgId/body/traceId`
  - 支持平台端手动重试
- [ ] 消费组：
  - `fixguild-notify-consumer`
  - `fixguild-stat-consumer`
  - `fixguild-audit-consumer`（可先留空）
- [ ] 实体映射注意：
  - `mq_consume_log`、`msg_fail` 是全局表（已在 `ignore-tables`），且没有 `create_by/update_by/remark`，不要直接继承 `BaseEntity`
  - `sys_notification` 是租户表，但没有 `update_by/update_time/remark`，使用轻量实体并保留 `is_delete` 逻辑删除
  - 所有轻量实体的 `tenant_id` 加 `@Column(tenantId = true)`（全局表除外）

### 4.4 通知

- [ ] `sys_notification` 表、实体、Mapper、Service
- [ ] 通知接口：
  - 租户端 `POST /tenant/api/notification/page`
  - 租户端 `POST /tenant/api/notification/read`
  - 技师端 `POST /technician/api/notification/page`
  - 技师端 `POST /technician/api/notification/read`
- [ ] Mock 短信：日志输出手机号掩码 + 内容，不接真实供应商
  - 承接 M2 移交的 `POST /account/api/{client}/sms/send`
  - 固定验证码或日志输出，1 分钟 1 次、1 天 10 次本地限流
- [ ] 通知消费逻辑：
  - 派单通知技师
  - 接单/拒单通知调度员
  - 完工通知客户/调度员
  - 取消通知相关人
  - 超时通知调度员

### 4.5 定时任务

- [ ] `workOrderSlaJob`：每 5 分钟扫描 `expect_time < now and timeout_flag = 0`，每批 200 条
- [ ] `workOrderAutoConfirmJob`：每小时将 `COMPLETED` 超过 7 天的工单自动 `CONFIRMED`
- [ ] `workOrderDailyStatJob`：每天 01:00 生成每日统计
- [ ] `mqFailRetryJob`：每 10 分钟按 `next_retry_time` 重发 `msg_fail`
- [ ] 所有任务：
  - 分布式锁防多实例重复执行（M5 提供后接入；M4 先用 XXL-Job 路由策略单机）
  - 按 id 分批，每批 200 条
  - 幂等：重复执行结果一致
  - 日志带 `jobId/traceId/处理数量`

### 4.6 测试

- [ ] 生产者：事务回滚不发消息；提交后发送
- [ ] 消费者：重复消息只处理一次
- [ ] 消费者异常：更新 `FAILED` 并触发重试
- [ ] 超过重试次数：进入 `msg_fail`
- [ ] 超时任务：重复执行不会重复提醒
- [ ] 自动确认：只处理超过 7 天的 `COMPLETED`
- [ ] MQ 失败重试任务：重试成功后可再次消费

## 5. 验收标准

- [ ] 工单状态变更后，通知消费者能收到消息
- [ ] 停掉消费者后重启，消息可重试
- [ ] 同一条消息重复投递只处理一次
- [ ] 超过重试次数的消息进入 `msg_fail`，可手动重试
- [ ] 超时任务重复执行不会重复提醒
- [ ] 自动确认任务只处理满足条件的工单
- [ ] `docker compose up -d` 可启动 MQ 与 XXL-Job
- [ ] `mvn test` 通过，文档与计划状态已同步

---

## 6. 风险与注意事项

- RocketMQ 5.x 与 4.9.x 配置差异较大，先固定一个版本跑通。
- 本地 MQ 环境较重；如果启动成本过高，先用 Spring Event + `@Scheduled` 过渡，但接口和消费幂等模型保持不变。
- 不要在事务内直接发 MQ；必须事务提交后发送。
- 消费失败不要吞异常，否则 RocketMQ 不会重试。
- 消费幂等表要尽早插入，避免业务先执行、幂等记录后写入。
- 超时任务必须有 `timeout_flag` 条件，避免重复提醒。
- 通知内容中的手机号必须掩码。
